# ADR-0002 - Adopt a Modular Repository Structure

## Status

Accepted

---

## Date

2026-07-18

---

## Context

The AI Local Lab is expected to evolve over time from a single AI coding agent into a complete local AI platform.

Future services may include AI agents, databases, web interfaces, monitoring tools, local LLMs and automation components.

Without a clear repository structure, the project would become difficult to navigate, maintain and extend.

A modular layout is required to separate infrastructure, documentation, automation scripts and application services.

---

## Decision

The repository will follow a modular directory structure where each top-level directory has a single responsibility.

The initial project layout is defined as follows:

```text
ai-local-lab/
│
├── adr/
├── backups/
├── compose/
├── docs/
├── scripts/
├── services/
├── stacks/
├── volumes/
│
├── README.md
├── LICENSE
├── .gitignore
└── .env.example
```

---

## Directory Responsibilities

### adr/

Architecture Decision Records.

Stores every architectural decision made throughout the project.

---

### docs/

Project documentation.

Includes architecture, deployment guides, audit reports and technical documentation.

---

### compose/

Shared Docker Compose files used to orchestrate services.

---

### services/

Contains individual service definitions.

Each service maintains its own Dockerfile, configuration files and documentation.

Example:

```
services/
    claw-code/
    ollama/
    open-webui/
```

---

### stacks/

Multi-service deployments.

Each stack combines several services into a functional environment.

Example:

```
stacks/
    development/
    production/
    experimentation/
```

---

### scripts/

Automation scripts used during deployment, maintenance and backups.

---

### volumes/

Persistent data generated by containers.

This directory is excluded from Git.

---

### backups/

Offline backups of important data.

---

## Rationale

A modular repository structure improves maintainability by separating concerns.

Each component has a well-defined location, reducing ambiguity and making the project easier to understand for contributors.

This approach also scales naturally as additional AI services are introduced.

---

## Alternatives Considered

### Flat Repository

Everything stored at the repository root.

Advantages

- Very simple.

Disadvantages

- Poor scalability.
- Difficult navigation.
- Files become disorganized over time.

Decision

Rejected.

---

### Service-Oriented Layout Only

Organize everything around services.

Advantages

- Simple for very small projects.

Disadvantages

- Documentation and infrastructure become tightly coupled.
- Harder to manage cross-cutting concerns.

Decision

Rejected.

---

## Consequences

### Positive

- Clear project organization.
- Easy onboarding.
- Better scalability.
- Consistent documentation.
- Supports future services.

### Negative

- Slightly larger directory hierarchy.
- Requires discipline to keep responsibilities separated.

---

## Impact

All future development must follow this repository structure.

New services should be added under the `services/` directory unless a different architectural decision supersedes this ADR.
